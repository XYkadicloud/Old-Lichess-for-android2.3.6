# 第一部分：给用户（你）的操作手册

## 1. 你要准备什么
- 手机：Samsung GT-S5360（Galaxy Y），Android 2.3.6。
- 一根数据线，或者让 Agent 把 APK 放到你能下载的地方（网盘、GitHub Release 等）。
- 手机能连 Wi-Fi。
- 一个 Lichess 账号（免费注册：lichess.org）。
- 一个 Lichess **API 令牌**（个人访问令牌）：
  1. 用电脑或别的手机浏览器登录 lichess.org。
  2. 打开 `https://lichess.org/account/oauth/token`。
  3. 创建新令牌，勾选 **Play games with the board API**（board:play），可再勾选读取账号信息。
  4. 复制令牌（形如 `lip_xxxxxxxx`），**不要发给任何人，包括 Agent 的聊天记录里也不要贴**。App 里会有输入框，只在手机上输入。

> 你不需要在电脑上装任何开发软件。APK 由 Agent 的环境（或云端 CI）构建。

## 2. 在手机上安装 APK
1. 手机：设置 → 应用程序 → 勾选 **未知来源**（允许安装非市场应用）。
2. 把 APK 拷到手机（USB 存储模式、蓝牙、或手机浏览器直接下载）。
3. 用文件管理器打开 APK → 安装。
4. 更新版本时：直接覆盖安装；若提示签名冲突，先卸载旧版再装（会丢失设置，需要重新输入令牌）。

## 3. 每一轮测试怎么做
1. 装上 Agent 给的新 APK。
2. 按下面的**测试清单**逐项试。
3. 遇到问题就记录，按**bug 报告模板**发给 Agent。
4. 收到修复版 APK，重复。

# 第二部分：给 Agent 的技术规格

## A. 项目目标
为 **Samsung GT-S5360（Android 2.3.6，API 10）** 开发一个轻量的原生 Lichess 客户端，使用 Lichess **Board API** 进行下棋。用户零编程基础，无法使用 adb/模拟器，所有调试依赖 **App 内日志与崩溃报告** 加用户的文字/截图反馈。

## B. 设备约束（必须遵守）
| 项目 | 值 |
|------|----|
| 系统 | Android 2.3.6（API 10） |
| CPU | ARMv6（ARM11, ~832MHz）→ 原生库只能用 `armeabi`，**不能**用 `armeabi-v7a` |
| 内存 | 约 290MB 总量，App 可用堆很小（约 24–32MB），**必须控制内存** |
| 屏幕 | 320×240（QVGA，ldpi，约 120dpi）→ 只做 **竖屏** 或按 240×320 设计 |
| 存储 | 内部空间紧张，APK 目标 < 5MB |
| 其他 | 无 SNI 支持、TLS 仅 1.0、无现代根证书（见 D 节） |

**开发硬性规则**
1. `minSdkVersion=10`，`targetSdkVersion=10`（或不高于 15）。
2. **不使用** AndroidX、AppCompat、Material、Fragment 支持库（它们最低要求 API 14+）。使用原生 `android.app.Activity`、`View`、`Canvas`。
3. Java 语言级别 **1.7 或以下**（无 lambda、无 try-with-resources 的 API 依赖需谨慎；`java.util.Objects` 等 API 19+ 的类**不可用**）。写完后对照 API 10 文档检查是否调用了更高版本 API。
4. 构建工具：使用**仍支持 minSdk 10 的旧版** Android Gradle Plugin 与对应 Gradle（Agent 需自行验证版本组合），JDK 建议 8。若环境搭建困难，可改用 Ant/命令行 `aapt + javac + dx`，或在 **GitHub Actions** 上构建并输出 APK。
5. 使用 ProGuard/R8（若可用）缩减体积，避免 dex 方法数超限（不要引入 multidex）。
6. 所有网络操作在**后台线程**，UI 更新用 `Handler`/`runOnUiThread`。可用 `AsyncTask` 或自管 `Thread`；不要用 Executor 以外的现代并发 API。
7. 不使用 WebView 加载 lichess.org（2.3 的 WebView 不能运行）。

## C. 功能范围

**V1（最小可用）**
- 设置页：输入/保存 API 令牌（`SharedPreferences`，令牌不写日志）。
- "测试连接"：调用 `GET /api/account`，显示用户名。
- 棋盘：`Canvas` 绘制 8×8，棋子用小尺寸位图或用 Unicode/矢量简绘。
- 对局：
  - 创建对局或接受挑战（先做"挑战 Lichess AI"和"公开匹配一局"其中一种最容易的，再扩展）。
  - 走子（点选→点落子）。
  - 实时接收对手走子、时钟、对局结束。
  - 认输、和棋提议/接受。
- 日志系统与崩溃报告（见 F 节）。

**V2（可选）**
- 观战、对局历史、每日挑战、升变选择界面优化、简易音效。

**V3（可选）**
- NDK 编译 Stockfish（`armeabi`），本地对弈/分析，限制深度。

## D. 关键技术难题：HTTPS 与 TLS（最大风险）

**已知事实（Agent 需实测验证）**
- Android 2.3 的 `HttpsURLConnection` 与 Apache `HttpClient` **不发送 SNI**；Lichess 前面有 CDN/反向代理，缺 SNI 时会握手失败或返回错误证书。
- 系统默认只启用 TLS 1.0；Lichess 通常要求 TLS 1.2+。
- 系统根证书库很旧，缺少 ISRG Root X1 等新根证书。

**推荐方案：App 内自带 TLS 客户端**
1. 引入 **Spongy Castle**（Android 用的 Bouncy Castle 重打包）或其他纯 Java、支持 TLS 1.2 的实现，使用其 `TlsClientProtocol` 自行建立 TLS 连接，**显式设置 SNI（server_name 扩展）**。
2. 在 App 的 assets 里内置所需根证书（ISRG Root X1、及 Lichess 当前证书链所需根；以实测为准），自建 `TrustManager`/证书校验，**不得关闭证书校验**。
3. 在其上实现一个极简 HTTP/1.1 客户端（GET/POST、`Authorization: Bearer <token>`、`User-Agent`、分块传输 `chunked` 解码、NDJSON 流式读取、长连接与超时/重连）。
4. 先写一个"网络诊断"页面：依次显示 DNS 解析、TCP 连接、TLS 握手（协议版本、证书链、是否 SNI）、HTTP 响应码，供用户拍照反馈。这是验证阶段 1 的核心工具。

**备用方案（仅当方案 1 在真机上无法成功时）**
- 由用户自己控制的中转服务（如自有服务器/局域网设备）提供 HTTP→HTTPS 转发。令牌会经过中转，**必须明确告知用户风险，不得使用不受信任的公共代理**。用户零基础且不想装东西，此方案是最后手段，需单独征求用户同意。

## E. Lichess API 使用要点
（Agent 开发时以 Lichess 官方 API 文档 `https://lichess.org/api` 为准并核对当前最新行为。）
- 认证：`Authorization: Bearer <token>`。
- 账号：`GET /api/account`。
- 事件流：`GET /api/stream/event`（NDJSON，含 `challenge`、`gameStart`、`gameFinish` 等；空行为心跳）。
- 对局流：`GET /api/board/game/stream/{gameId}`（首行 `gameFull`，后续 `gameState`、`chatLine`、`opponentGone`）。
- 走子：`POST /api/board/game/{gameId}/move/{uci}`（UCI 格式，如 `e2e4`，升变 `e7e8q`）。
- 认输：`POST /api/board/game/{gameId}/resign`；和棋：`POST /api/board/game/{gameId}/draw/{yes|no}`。
- 挑战 AI：`POST /api/challenge/ai`；公开匹配：`POST /api/board/seek`（流式，保持连接期间有效）。
- 遵守速率限制：遇到 HTTP 429 至少等待 60 秒；同一时间不要多开事件流。
- 流式 JSON 用**逐行读取**解析（Android 内置 `org.json` 即可），不要一次性读完整个响应。

## F. 日志、崩溃报告、诊断（为"无 adb 调试"而设）
1. **自建 Logger**：环形缓冲区（约 500 行）加写文件 `/sdcard/LichessOld/log.txt`（限制大小如 512KB，自动轮转）。每行含时间、级别、模块、信息。
2. **令牌与敏感信息脱敏**：日志中 `Bearer` 之后的内容一律替换为 `***`。
3. **未捕获异常处理**：`Thread.setDefaultUncaughtExceptionHandler` 把堆栈写入 `/sdcard/LichessOld/crash.txt`；下次启动时弹窗提示"上次崩溃，是否查看/保存报告"。
4. **"查看日志"页面**：滚动显示最近日志，字体足够大；有"保存到存储卡"、"清空"按钮。
5. **版本号显示**：设置/关于页显示 `versionName` 与构建时间，用户报 bug 时必填。
6. **网络诊断页**：见 D 节第 4 点。
7. **调试模式开关**：开启后记录更详细日志（网络请求行、状态码、耗时，不含令牌与完整响应体）。

## G. UI 规格（320×240）
- 竖屏，单 Activity 或少量 Activity，界面元素少而大。
- 棋盘占屏幕宽度（约 240px 宽，每格 30px），棋子位图 30×30 或 28×28。
- 文字最小 14sp 左右，按钮高度不少于 40px，方便触摸。
- 主界面：`开始对局`、`设置`、`日志`、`网络诊断`。
- 对局界面：上方对手信息与时钟，中间棋盘，下方我方信息与时钟，底部按钮（认输/和棋/返回）。
- 走子高亮：选中格、可落子格；最近一步高亮。

## H. 分阶段计划与验收标准
> 原则：**一次一个阶段，用户真机验证通过再进入下一阶段**。每个阶段交付一个带版本号的 APK 加一份"本阶段变更与需要用户测试的项目"清单。

### 阶段 0：项目骨架（预计 1 天）
- 建立项目、构建流程（本地或 CI），输出可安装的 Hello APK。
- 内置版本号显示、日志系统、崩溃报告雏形。
- **验收**：用户能安装，App 打开显示"版本号 + Hello"，点"日志"能看到启动记录。

### 阶段 1：网络与 TLS（预计 3–7 天，风险最高）
- 实现"网络诊断"页面与自带 TLS 客户端。
- 目标请求：`GET https://lichess.org/api/account`（无令牌时应返回 401，说明握手与 HTTP 成功）。
- **验收**：诊断页显示 TLS 握手成功、协议版本、证书链校验通过、收到 HTTP 401（或带令牌后 200）。若失败，页面必须显示具体失败步骤和异常信息，供用户拍照回报。

### 阶段 2：登录与账号（预计 1–2 天）
- 令牌输入与保存，"测试连接"显示用户名。
- **验收**：用户看到自己的 Lichess 用户名；令牌错误时有明确提示；日志无令牌明文。

### 阶段 3：棋盘与本地规则（预计 3–5 天）
- 棋盘绘制、点选走子、合法着法判断（可自写或用兼容 Java 7/API 10 的库；引入前检查方法数与体积）、升变选择、将军/将死/逼和检测。
- 离线"本地双人"模式便于用户单独测试界面。
- **验收**：用户在离线模式下能完整走完一局；非法走子被拒绝；界面在 320×240 上不溢出。

### 阶段 4：接入对局（预计 4–7 天）
- 事件流、对局流、走子、时钟、认输、和棋。
- 先做"挑战 AI"（最容易在真机上单人验证），再做公开匹配。
- 断线重连：流断开后自动重连并用 `gameFull` 同步状态；指数退避。
- **验收**：用户能与 Lichess AI 下完一局；手机走子在 lichess.org 网页上可见；后台/锁屏恢复后状态正确。

### 阶段 5：稳定性与性能（预计 3–5 天）
- 内存：位图缓存、及时释放；峰值堆使用记录到日志。
- 电量：无对局时不保持流连接；屏幕关闭时暂停非必要刷新。
- 错误处理：所有网络错误对用户显示简短中文提示，并写入日志。
- **验收**：连续 20–30 分钟对局无崩溃、无 OOM；在网络切换情况下能恢复。

### 阶段 6（可选）：V2/V3 功能
- 观战、历史、本地 Stockfish（`armeabi`，深度限制）等。逐项征求用户意愿。

## I. Agent 的工作纪律
1. **每次交付必须包含**：APK 文件（或下载链接）、版本号、变更摘要、"请用户测试的项目"清单（用第一部分表格编号对应）。
2. 收到用户 bug 报告后：先**复述你理解的问题与推测原因**，再改代码；修复后说明如何验证。
3. 不能确定的行为（如 TLS 是否成功、某 API 在 API 10 是否可用）**必须通过真机日志验证**，不要假设"应该可以"。
4. 遇到需要用户做的操作，用**零基础能看懂的中文步骤**说明，一次只让用户做一件事。
5. 任何会让用户令牌离开手机（例如中转代理）的设计，必须先得到用户明确同意。
6. 保持依赖最少，保证 APK 体积与内存占用小；每次新增依赖需说明原因与体积影响。
7. 不得关闭 TLS 证书校验来"让它跑通"。
8. 代码结构清晰，`README` 中记录：构建方法、目录结构、已知问题、版本历史，方便以后接手。

## J. 已知风险清单
| 风险 | 影响 | 应对 |
|------|------|------|
| TLS 1.2 + SNI 在 API 10 上自实现失败 | 无法连上 Lichess | 网络诊断页逐步定位；备用中转（需用户同意） |
| 旧版构建工具链难以配置 | 无法出 APK | 用 GitHub Actions/Docker 固定旧版工具链 |
| 内存不足/OOM | 闪退 | 小位图、少缓存、日志记录堆使用 |
| Lichess API 将来变动 | 功能失效 | 日志中记录 HTTP 状态与错误；README 记录 API 依赖点 |
| 证书更新，内置根证书过期 | 突然连不上 | 诊断页显示证书链信息；预留更新证书的方法 |
| 用户无法提供有效日志 | 排错困难 | 崩溃自动报告、日志一键保存、诊断页拍照即可 |

## K. 开工提示词（可直接发给 Agent）
> 请阅读本文档全文，并按"第二部分"的规格开始 **阶段 0**。先告诉我：（1）你打算如何构建 APK（本地环境或 CI），（2）你需要我提供或确认什么。之后每完成一个阶段，请给我 APK、版本号和测试清单，等我在真机上测完再继续。我完全没有编程基础，请用简单的中文一步一步告诉我该做什么。
